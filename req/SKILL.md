# req — Full-Cycle Development Workflow

## 1. Role
You are the full-cycle development orchestrator. You assess each task, identify its domain, build a tailored pipeline, and drive execution through it. All stages (analyze → tech → code → security → cleanup → review → verify → amend → justify) are documented here as references — the orchestrator reads the relevant section and executes it directly.

## 2. Directory Structure

```
requirements/
├── index.md                 # Domain directory (English only)
├── architecture.md          # Tech philosophy, principles, structural decisions
├── CATALOG.md               # Auto-generated project abstract memory
└── {domain}/
    ├── README.md            # Domain overview + simple scenarios inline
    └── {scenario}.md        # Complex scenarios get separate files

.claude/skills/              # Domain knowledge skills (auto-generated by req-domain-skills-generate)
└── project-description-skills/
    ├── SKILL.md             # Main entry — domain index + architecture overview
    └── {domain}.md          # Per-domain knowledge, patterns, pitfalls, hooks
```

## 3. Pipeline Orchestration

### 3.1 Entry — Task Classification

Run FIRST, every time. Read `requirements/index.md` before deciding anything.

| Scenario | Description | Action |
|----------|-------------|--------|
| **A — Trivial** | rename variable, add log, tweak config | Execute directly, no docs |
| **B — New work** | New feature needing domain docs | Identify domain → pipeline |
| **C — Amend (spec)** | Existing scenario, direction changed | Amend docs → re-run affected stages |
| **D — Amend (bug)** | Implementation defect | Amend docs → code → verify |
| **E — Ambiguous** | Might be existing or new | Check existing scenarios → amend or new |

### 3.1b Pipeline Bootstrap

Before starting the pipeline, ensure project knowledge infrastructure exists:

1. Check if `.claude/skills/project-description-skills/SKILL.md` exists in the project
2. If **not found** → call `Skill("req-domain-skills-generate")` to generate the full project-description-skills from existing `requirements/` docs and source code
3. If **found** → continue to triage and pipeline
4. After pipeline completes → §4.10 (Skills Sync) will refresh the domain just worked on

### 3.2 Pipeline Triage

| Stage | Skip when |
|-------|-----------|
| analyze | User provides complete spec (rare) |
| tech | Change is mechanical ("delete X", "rename Y") |
| code | **Never skip** |
| security | No new attack surface: refactor, internal wiring, no user input/auth |
| cleanup | The change IS cleanup, OR scope ≤ 3 files |
| review | Scope ≤ 3 files AND no functional changes |
| verify | Pure refactoring/deletion, existing tests sufficient |
| justify | **Never skip** |

### 3.3 Pipeline Plan

Present pipeline and wait for user confirmation:

```
Pipeline for {domain}/{scenario}:

  ✓ analyze    — 需求分析
  ✓ tech       — 技术方案
  ✓ code       — 编码
  ✗ security   — 跳过（原因）
  ...
  ✓ justify    — 论证（必做）

调整？（"+security" 加回，"-review" 跳过，或直接开始）
```

### 3.4 Execution

```
for each active stage in order:
  1. Inform user: "Starting: {stage} ({domain}/{scenario})"
  2. Execute:
     - amend: Call Skill("req-amend", "{domain}/{scenario}")
     - All other stages: Read the relevant Stage Reference (§4.X) and execute
  3. Apply routing rules (§3.5) based on Stage Result
```

The amend stage delegates to the standalone `req-amend` skill. Catalog is not a pipeline stage — run `/req-catalog` independently when needed.

### 3.5 Routing Rules

**After review**: `all_satisfied` → next stage; `has_gaps` → route back to code, re-run review (max 3 loops)

**After verify**: `all_pass` → next; `has_failures` → route back to code, re-run verify (max 3 loops)

**After amend**: `significant` → route to tech; `approach_only` → route to code; `minor` → continue

**After security**: `pass/conditional_pass` → continue; `fail` → halt, inform user

**After cleanup**: `integrity: pass` → continue; `integrity: fail` → cleanup reverted, continue

**After justify**: `all_justified` → finish; `has_issues` → present to user

### 3.6 Post-pipeline

After justify completes (all stages done), if domain skills exist in `.claude/skills/`, run §4.10 (Skills Sync) to refresh them.

Catalog regeneration (`requirements/CATALOG.md`) is a separate action — run `/req-catalog` independently when needed.

## 4. Stage References

### 4.1 Analyze — Requirement Analysis

**Purpose**: Expand a brief description into complete domain scenario documents.

**Steps**:
1. **Understand** — If argument is empty, ask: what feature, what problem, who users, any references?
2. **Triage** — Fast path (clear direction, refactor) vs Deep path (multiple directions, cross-cutting)
   - Deep: launch parallel subagents (Agent A: core MVP, Agent B: full scope), then Agent C: core conflict analysis
   - Present diverge-converge synthesis, wait for user selection
3. **User review** — Loop until user approves
4. **Determine domain** — Read `requirements/index.md`, match or propose new domain
5. **Domain knowledge hook** — Load `Skill("project-description-skills")` to incorporate domain expertise (patterns, terminology, constraints)
6. **Write docs** — Per the format below
7. **Diagrams** — At least one use case diagram for new domains (see `_shared/plantuml.md`)
8. **Update index.md** — Add domain row if new

**Document format**:
```
# {Domain Name}

> {Description}

## Scenarios

| Scenario | Location |
|:---|:---|

# {Concern Area}

## US-XX: As a {actor}, {situation/need}, so that {value}

{1-2 sentences: what and why — pure business language}

### Acceptance Criteria
- Given {context}, when {action}, then {observable outcome}
```

**User story actors**: cycle, agent, evaluator, operator, tool, CI pipeline

**Writing rules**:
- One story = one concern, include "so that" rationale
- NO function/class/variable names
- Acceptance criteria in Given/When/Then
- Section headings in English only
- Standalone scenario files need YAML frontmatter (name + description)

**Stage Result**:
```
## Stage Result
- **status**: completed
- **domain**: {domain name}
- **scenario**: {scenario name}
- **user_stories**: US-01, US-02, ...
```

### 4.2 Tech — Technical Design

**Purpose**: Think through implementation approach, update scenario docs and architecture.md.

**Prerequisites**: Scenario document exists with requirements drafted.

**Steps**:
1. **Read** scenario doc + architecture.md + scan codebase
2. **Domain knowledge hook** — Load `Skill("project-description-skills")` for tech guidance (architecture patterns, technology choices, extension conventions)
3. **Triage** — Fast (mechanical changes) vs Deep (new module, multiple approaches)
   - Deep: parallel agents (Agent A: simple direct, Agent B: extensible), then conflict analysis
4. **Write/update Implementation Approach** section:
   ```markdown
   ## Implementation Approach
   ### Technology Stack
   | Module | Technology | Rationale |
   
   ### Module Design
   #### {Module}
   - Responsibility:
   - Files to modify:
   - Public interface:
   
   ### Superseded Components
   | Component | Path | Superseded By | Cleanup Action |
   
   ### Risks & Notes
   ```
5. **Update architecture.md** — Only for structural decisions:
   - Core Patterns: Structure, Contract, State flow, Extension, Invariants
   - Interface Contracts: Producer, Consumer, Wiring, Contract, Verified by
   - Key Decisions, Extension Guide, Glossary, Overview
6. **Diagrams** if needed (architecture, sequence — see `_shared/plantuml.md`)

**Stage Result**:
```
## Stage Result
- **status**: completed
- **domain**: {domain name}
- **scenario**: {scenario name}
- **modules**: {N} modules defined
- **architecture_updated**: yes | no
```

### 4.3 Code — Implementation

**Purpose**: Write code following domain docs and architecture.md.

**Steps**:
1. **Read** scenario document + architecture.md + Implementation Approach section
2. **Load language conventions** — Read `conventions/{language}.md` if available in this skill directory
3. **Domain knowledge hook** — Load `Skill("project-description-skills")` for implementation patterns and pitfall avoidance
4. **Write tests first** — Generate failing tests from acceptance criteria
5. **Implement module by module** — Parallel subagents for independent modules
6. **After each module**: Check requirement alignment → inline code review → cleanup superseded components → commit
7. **Generate automation scripts** — `scripts/build.{bat|sh}`, `scripts/run.{bat|sh}`, `scripts/test.{bat|sh}`

**Code quality**:
- High cohesion, low coupling
- 2-occurrence rule: same logic in 2+ places → extract to shared utility
- Variable/function names, comments, logs in English only

**Logging** (every piece of code):
| Level | When |
|:---|:---|
| info | Key business milestones |
| debug | Intermediate values, branch decisions |
| warn | Expected failures (validation, retry) |
| error | Unexpected failures (DB, service) |

**Methods as Documentation** — Public methods read like flowcharts:
```
def do_action(self, data):
    # 1. Validate
    self._validate(data)
    # 2. Enrich defaults
    enriched = self._enrich(data)
    # 3. Persist
    record_id = self._save(enriched)
    # 4. Notify
    self._notify(record_id)
    # 5. Return
    return self._build_result(record_id)
```

**Stage Result**:
```
## Stage Result
- **status**: completed
- **domain**: {domain name}
- **scenario**: {scenario name}
- **modules_implemented**: {list}
- **tests_written**: {N} test files
```

### 4.4 Security — Security Review

**Purpose**: Detect data security issues and code vulnerabilities.

**Steps**:
1. Scan all code produced for this scenario
2. Check: injection, auth flaws, sensitive data exposure, insecure deserialization, dependency vulnerabilities
3. **Fix critical/high issues** directly
4. **Report medium/low** issues (do not fix without user approval)

**Stage Result**:
```
## Stage Result
- **status**: pass | conditional_pass | fail
- **critical**: {N}
- **high**: {N}
- **medium**: {N}
- **low**: {N}
- **fixed**: {list}
```

---

### 4.5 Cleanup — Code Cleanup

**Purpose**: Structural optimization without changing business logic.

**Rules**: No behavior changes, no algorithm changes, no interface changes, no feature changes.

**Steps**:
1. Scan code for: unused imports/vars/functions, dead code, duplicate code, over-wrapping, zero-value comments
2. Present findings, **wait for user approval**
3. Apply approved changes
4. Verify: build must pass, all tests must pass

**Stage Result**:
```
## Stage Result
- **status**: completed
- **changes_applied**: {N}
- **integrity**: pass | fail
```

### 4.6 Review — Requirement Review

**Purpose**: Verify item by item that code satisfies the scenario document.

**Steps**:
1. Read scenario doc + architecture.md + locate all source files
2. **Domain knowledge hook** — Load `Skill("project-description-skills")` for review-hook domain-specific checklist
3. For every requirement/acceptance criterion: find code, classify as Implemented/Partial/Not implemented
4. Check superseded components were cleaned up
5. Check interface contracts are satisfied

**Comparison table**:
```
| Requirement | Status | Code Location | Notes |
|:---|:---|:---|:---|
| F-01 ... | Implemented | src/xxx.py:L20 | |
```

**Stage Result**:
```
## Stage Result
- **status**: all_satisfied | has_gaps
- **satisfied**: {N}/{M}
- **gaps**: {list of IDs if has_gaps}
```

### 4.7 Verify — Verification

**Purpose**: Ensure code builds, runs, and passes tests.

**Steps**:
1. **Identify project type** from scenario docs
2. **Build check**: tsc, mvn compile, go build, etc.
3. **Runtime check**: start and confirm it works
4. **Domain knowledge hook** — Load `Skill("project-description-skills")` for verify-hook domain-specific test strategies
5. **Automated tests**: Generate from acceptance criteria if none exist
6. **Update automation scripts**

| Technology | Build | Test |
|:---|:---|:---|
| Python | `python -m py_compile` or `mypy` | `pytest tests/ -v` |
| Java (Maven) | `mvn compile` | `mvn test` |
| TypeScript | `tsc --noEmit` | `npm test` |
| Go | `go build ./...` | `go test ./...` |

**Stage Result**:
```
## Stage Result
- **status**: all_pass | has_failures
- **build**: pass | fail
- **runtime**: pass | fail
- **tests**: {X}/{Y} passing
- **failures**: {list if has_failures}
```

### 4.9 Justify — Process Justification

**Purpose**: Meta-review of the process itself — validate each executed stage for reasonableness, reliability, efficiency.

**Three dimensions**:
| Dimension | Question |
|-----------|----------|
| 合理性 | Was scope/direction appropriate? |
| 可靠性 | Are outputs complete and accurate? |
| 高效性 | Any wasted effort or over-engineering? |

**Per-stage checklist**:
- **analyze**: Stories complete? Criteria testable? Concise?
- **tech**: Architecture matches complexity? Alternatives considered? Contracts documented?
- **code**: Faithful to design? Edge cases handled? No over-abstraction?
- **security**: Surface correctly identified? Fixes effective?
- **cleanup**: Right targets? Behavior preserved?
- **review**: Every item checked? Verdicts correct? (spot-check 2+)
- **verify**: Tests cover core paths? Deterministic?

For each issue found: fix directly (do not route back), then re-evaluate. Max 3 rounds.

**Stage Result**:
```
## Stage Result
- **status**: all_justified | has_issues
- **rounds**: {N}
- **fixed**: {N}
```

### 4.10 Skills Sync — Domain Skill Refresh

**Purpose**: Refresh `.claude/skills/project-description-skills/` for the domain just worked on in this pipeline.

**Execution**: `Skill("req-domain-skills-generate", "--pipeline-domain {domain}")`

This calls the standalone `req-domain-skills-generate` skill in incremental mode — only the pipeline's domain file (`{domain}.md`) is updated. The SKILL.md index is rebuilt after the domain update.
