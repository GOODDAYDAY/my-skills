# Diverge-Converge Pattern

> Version: v1 | Date: 2026-04-02

用于 Stage 1（需求分析）和 Stage 2（技术设计）的多 subagent 发散—辩论—收敛机制。

## 1. 模式定义

```
Stage Start
  ↓
Round 1 [并行]: Agent A（核心路径）| Agent B（完整视野）
  ↓
Round 2 [顺序]: Agent C（核心矛盾）— 读取 A+B 输出，找真正矛盾点
  ↓
Round 3 [并行]: Agent A v2 | Agent B v2 — 各自回应 C 的质疑，互相反驳或认可
  ↓
[Synthesis]: 主 agent 汇总 — 对比表 + 核心矛盾 + 推荐
  ↓
用户选择方向或描述如何合并
  ↓
Stage 继续
```

## 2. 三个角色

### Agent A — 核心路径（MVP Advocate）
- **约束**：Stage 1 最多 5 条 F-xx；Stage 2 模块数 ≤ 3，最少依赖
- **使命**：剔除一切非核心，对每个条目问"这是必须的吗？"
- **交付**：最快可交付的最小方案

### Agent B — 完整视野（Product Thinker）
- **约束**：无数量上限，必须覆盖所有合理场景含边界情况
- **使命**：对每个功能问"还缺什么？"，考虑长期演进；同时带入下游视角，标记安全敏感功能/模块（涉及用户输入、权限、外部 API、敏感数据）、验收条件模糊难测的项、高耦合或高重复的设计风险
- **交付**：完整可演进的方案，附带下游预警标注（每项标注不超过一句）

### Agent C — 核心矛盾（Strategic Challenger）
- **输入**：A 和 B 的完整输出
- **使命**：找出 A 和 B 之间最根本的分歧，判断"用户真正想解决的问题是什么，A 和 B 有没有跑偏"
- **交付**：① 具体命名的 A/B 核心矛盾点（不可模糊）；② 对"真实问题"的判断；③ 1-2 个双方方案中的下游风险预警（如"两个方案都没考虑 X 的权限控制"或"B 的模块划分让核心逻辑难以单独测试"）——预警不审查，只点名

## 3. Round 3 消息传递模型

Subagent 之间不直接通信，主 agent 扮演传话人：

- Round 3 启动 Agent A v2 和 Agent B v2（新实例，非续接 Round 1）
- 两者并行启动，互不感知，基于相同信息独立判断
- **每个 v2 实例的 prompt 必须包含**：
  1. 自己 Round 1 的完整原始方案
  2. 对方 Round 1 的完整方案
  3. Agent C 的质疑全文（完整，不裁剪）
  4. 任务说明：明确回应 C 的质疑；对对方方案提出反驳或认可，说明理由

## 4. Synthesis 输出格式

主 agent 整理后按此格式呈现（无需用户干预）：

**1. 三方立场速览**（各一句话）
- Agent A：...
- Agent B：...
- Agent C 质疑：...

**2. 核心矛盾点**（C 指出的具体分歧，如"A 假设用户只需单次触发，B 假设需要持续监控"）

**3. 对比表**

Stage 1（需求分析）：

| 维度 | Agent A（核心路径）| Agent B（完整视野）|
|:---|:---|:---|
| 功能覆盖 | | |
| 复杂度 | | |
| 交付速度 | | |
| 安全敏感点 | | |
| 可测试性 | | |

Stage 2（技术设计）：

| 维度 | Agent A（简单直接）| Agent B（可扩展）|
|:---|:---|:---|
| 模块数 | | |
| 复杂度 | | |
| 可维护性 | | |
| 适用场景 | | |
| 安全设计 | | |
| 可测试性 | | |
| 代码整洁度 | | |

**4. 推荐方向**（基于对话上下文的判断；可说明推荐 A、B 或融合方案，并说明理由）

---

然后等待用户选择：**选 A / 选 B / 描述融合方式**。

## 5. 实现约束

- **强制发散**：A 和 B 必须遵守硬性数量约束，保证产出真正不同的方向，而非同一方案的两种表述
- **C 必须具体**：C 必须点名具体矛盾点，禁止输出"两者各有优点"之类的模糊结论
- **真实 subagent**：所有 agent（A/B Round 1、C、A/B Round 3）均通过 `Agent` tool 启动，**不允许**主 agent 内部换角色模拟
- **主 agent 保持中立**：在 Synthesis 输出前，主 agent 不应对哪个方案"更好"作出暗示
- **完整传递**：Round 3 的 prompt 必须包含 A、B、C 的完整输出，不得裁剪或总结
- **下游预警是预警不是审查**：B 和 C 的下游视角只是在方案锁定前点出明显隐患，让用户带着这些认知做选择；req-4（安全）、req-5（清理）、req-7（验证）阶段仍会进行完整的专项检查，这里不替代它们
